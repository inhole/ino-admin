# Git 커밋 메시지 규칙

이 저장소의 커밋 메시지는 변경 이력을 빠르게 이해하고 자동화 도구에서 일관되게 처리할 수 있도록 아래 형식을 사용한다.

## 기본 형식

```text
type: 한글 변경사항
```

예시:

```text
feat: 관리자 샘플 목록 화면 추가
fix: 요청 추적 ID가 오류 응답에서 누락되는 문제 수정
docs: 로컬 개발 환경 실행 방법 보완
```

## Type 목록

| Type | 용도 |
|---|---|
| `feat` | 사용자에게 제공되는 새로운 기능 |
| `fix` | 오류 또는 잘못된 동작 수정 |
| `docs` | 문서만 변경 |
| `test` | 테스트 추가·수정 |
| `refactor` | 동작을 바꾸지 않는 코드 구조 개선 |
| `perf` | 성능 개선 |
| `style` | 포맷, 공백 등 동작과 무관한 변경 |
| `build` | 빌드 시스템 또는 외부 의존성 변경 |
| `ci` | CI/CD 설정 변경 |
| `chore` | 위 분류에 속하지 않는 유지보수 작업 |
| `revert` | 이전 커밋 되돌리기 |

## 작성 원칙

- `type`은 소문자로 작성한다.
- 콜론 뒤에 공백 한 칸을 넣는다.
- 변경사항은 한글 명사형으로 간결하게 작성하고 마침표를 붙이지 않는다.
- 제목은 무엇을 변경했는지 구체적으로 설명한다. `수정`, `작업`처럼 의미가 불분명한 제목만 사용하지 않는다.
- 한 커밋에는 하나의 논리적 변경만 포함한다.
- 관련 이슈가 있으면 본문 마지막에 `Refs: #123` 또는 `Closes: #123`을 작성한다.

## 본문과 호환성 변경

변경 이유나 운영 영향 설명이 필요하면 제목 다음에 빈 줄을 두고 한글 본문을 작성한다.

```text
feat: refresh token 재사용 탐지 추가

탈취된 refresh token이 다시 사용되면 같은 token family의 세션을 모두 폐기한다.

Refs: #42
```

호환되지 않는 API·설정·DB 변경은 본문에 `BREAKING CHANGE:`를 명시한다.

```text
feat: 사용자 검색 API 요청 형식 변경

BREAKING CHANGE: 검색 조건을 query parameter에서 JSON 요청 본문으로 변경한다.
```

## 피해야 할 예시

```text
수정
update files
Feat : 기능 추가.
feat: 여러 가지 작업
```
